# CascadeSpec four-round cadence at 32K

This is the fixed six-execution check for the new schedule:

1. MTP gamma 4, then sparse-target batch verification and optional extension.
2. Repeat the sparse round three times.
3. On round four, append up to four unchecked MTP tokens without a fourth sparse pass.
4. Verify the entire provisional block once with the dense target.

The provisional-token cap is 19, so the dense batch has at most 20 input rows including the
preceding committed token. Recurrent Qwen targets use full checkpoints every four input rows and
exact forward replay of at most three updates. Gemma4 has no recurrent target state and uses normal
KV-cache prefix trimming.

## Benchmark setup

- One plain MTP gamma-4 run and one CascadeSpec run per model.
- Native-chat OpenCode conversation fixture, 32,768-token budget.
- 128 generated tokens, temperature 0, seed 1234.
- Target and draft KV caches: q8_0/q4_0.
- Sparse ratios: Qwen27 10%, Gemma4 20%, Qwen35 20%.
- Direct sparse kernel.

## Result

| Model | Plain MTP tok/s | CascadeSpec tok/s | Change | Plain dense cycles | Cascade sparse + dense passes | Committed per dense cycle |
|---|---:|---:|---:|---:|---:|---:|
| Qwen27 | 55.26 | 30.77 | -44.3% | 33 | 44 + 15 | 8.47 |
| Gemma4 | 51.71 | 36.33 | -29.7% | 43 | 46 + 16 | 7.94 |
| Qwen35 | 168.02 | 90.14 | -46.4% | 34 | 39 + 13 | 9.77 |

The schedule reduced dense-verification frequency, but not total target-model work. Each sparse
pass was too close to the cost of an ordinary gamma-4 dense pass:

| Model | Plain gamma-4 dense pass | Sparse pass | Sparse saving | Final large dense pass |
|---|---:|---:|---:|---:|
| Qwen27 | 57.27 ms | 54.40 ms | 5.0% | 63.13 ms |
| Gemma4 | 47.58 ms | 42.75 ms | 10.1% | 62.57 ms |
| Qwen35 | 15.45 ms | 16.26 ms | -5.2% | 28.54 ms |

The sparse middle stage also changed the provisional branch enough that dense acceptance was only
60.5% on Qwen27, 64.2% on Gemma4, and 70.8% on Qwen35. Thus CascadeSpec performed substantially
more target passes, more MTP drafting, and a larger final dense pass.

## State integrity and output hashes

All runtime integrity counters were zero on every model: no snapshot failures, rollback failures,
position mismatches, or recurrent-prefix restore failures. Qwen27 completed 59 periodic prefix
restores and Qwen35 completed 52; replay depths covered zero through three updates.

The CascadeSpec output hashes did not equal the plain-MTP gamma-4 hashes. This is retained as a
diagnostic, not treated as evidence of recurrent replay corruption. Gemma4, which has no recurrent
state, also differed. Moreover, earlier same-prompt plain-MTP runs changed the Gemma4 and Qwen35
hashes when gamma changed from 3 to 4. A different verification batch shape changes floating-point
rounding and can change a greedy token at a low-margin position.

Exact recurrent-state replay is separately covered by `test-recurrent-replay-model`, which compares
the restored recurrent tensors, positions, continuation logits, selected tokens, and output hashes
against stride-one snapshots generated by the same 20-row target pass.
